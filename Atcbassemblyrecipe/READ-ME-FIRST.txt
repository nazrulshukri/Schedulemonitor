TWO THINGS IN THIS DROP
=======================

1. THE RELATIONSHIP YOU ASKED FOR
---------------------------------
AWACSWSTYPE is the parent (one row per machine, keyed by WSID).
TBLWIREBOND is the child (one row per recipe). The child had nothing
pointing back at the parent, which is exactly why saving a recipe could
not touch AWACSWSTYPE - there was no machine on the recipe to relate.

TBLWIREBOND now has a WSID column, the same way TBLSAWING.SAWMACHINE
holds WSID values like DS12-004.

   RUN: Database/tblwirebond-wsid.sql     (F5, whole file)

Then on the Wirebond page, Machine is a dropdown of the wire bonders
registered in AWACSWSTYPE. Register them first if you have not:
Operations > AWACSWSTYPE > Add Row, WSTYPE WIREBOND.

The reference is checked in the DATABASE on every save - add, edit and
CSV import all refuse a machine that is not registered as a wire bonder.
Step 4 of that script adds a real foreign key too, if your AWACSWSTYPE
has no duplicate WSIDs.

Saving a recipe still does not WRITE to AWACSWSTYPE, and should not - the
machine record did not change. What changed is that the recipe now names
its machine, so the two tables join.


2. A BUG I INTRODUCED, AND THE FIX
----------------------------------
Your screenshot showed AWACSWSTYPE.WSDB holding SENSORS and POWER. It is
the machine's BUSINESS GROUP - it matches SAWBFG in TBLSAWING. It is not
a table name.

The app had it wrong, and the version I sent you yesterday made it worse:
it derived WSDB from WSTYPE and wrote TBLSAWING / TBLWIREBOND into that
column on EVERY save, including edits of existing rows. Editing a machine
whose WSDB was SENSORS would have silently replaced it with TBLSAWING.

Fixed in this drop. WSDB is a normal field on the AWACSWSTYPE grid now,
with the values already in your table offered as a pick list. Nothing
derives or overwrites it.

   RUN: Database/awacswstype-wsdb-repair.sql
        Block 1 shows which WSDB values are in the table. If TBLSAWING
        appears, block 2 lists the affected rows and suggests the right
        value from TBLSAWING.SAWBFG, and block 3 applies it.

If you have not yet rebuilt with yesterday's drop, only rows added
through the page carry TBLSAWING - no existing row was overwritten.
